# 出题 Agent 与解题 Agent 设计

日期：2026-08-30  
状态：已落地（V1 探索模式）；本文整理既有思路，不是新开一条实现线  
产品：小欧手机 H5（`/`）。`/v2/` 体素工坊不走这条链路。

---

## 1. 一句话

出题的人只写题，不陪练；陪练的人只教这张题，不再另出题。画板上的对错由程序说了算，两个模型都不能直接画画。

---

## 2. 为什么拆成两个 Agent

早期是一次 LLM 调用既出题又教。这样有三个结构性问题：

1. **出题和教学互相污染。** 模型为了好教，会把题出浅；为了出得漂亮，又会在对话里提前泄底。
2. **画板没有权威。** 模型一边说话一边吐 SVG / `xiaoou-draw` / 临时 JSON，前端无法稳定渲染，孩子看到的图和嘴里说的数经常对不上。
3. **无法验收。** 题好不好、教得好不好，缠在同一段生成里，没法单独校验、单独换模型、单独重试。

所以拆成两个角色、三次确定性中间层：

| 角色 | 孩子看不看得见 | 产出 | 禁止 |
|------|----------------|------|------|
| **出题 Agent（Author）** | 看不见 | 一张 JSON 题卡 | 讲解、陪练、发明画图协议 |
| **解题 Agent（Tutor）** | 看得见（小欧） | 一句追问 + 受控工具 | 另出题、直接报答案、输出画图 JSON |
| **程序中间层** | 部分可见 | 画板、第一问、课状态、工作区 | 把教学路线写成固定剧本 |

Author 可以换成更强的模型、开思考；Tutor 用更稳的陪练模型、默认关思考。两边失败互不影响：出题失败用种子题卡；工具失败回退到上一张有效盘面，对话继续。

---

## 3. 总原则

1. **约束动作，不约束思路。** 程序规定 Tutor 能对数学世界做哪些可验证的动作；不规定必须先问 A 再问 B。
2. **画板真相在程序侧。** Author 只描述数学模型；服务端校验成 BoardSpec V3；前端确定性渲染。Tutor 用工具改工作区，不能改像素。
3. **insight 永不进入孩子可见面。** 题卡里的「要发现的道理」只给 Tutor 看。字幕、气泡、发现芯片都只能用孩子自己的话。
4. **第一问由程序写。** 开场白等于 `first_question`，不调 LLM 打招呼，避免模型改写、泄底或换成 9 块正方形。
5. **一次只问一个问题。** 卡住给最小台阶；答错不说「错了」，用反例。
6. **换主题必须换学具和故事。** 除了「连续奇数相加得平方数」，禁止用 9 块摆正方形当第一问。

## 4. 分工总图

```text
孩子（手机 H5）
   │
   │ 选主题 / 点开始玩          说话、拖积木、点「太难了」
   ▼                            ▼
POST /api/author            POST /api/chat  (SSE)
   │                            │
   ▼                            ▼
┌──────────────┐            ┌─────────────────────┐
│ 出题 Author   │            │ 解题 Tutor Agent     │
│ GLM / DeepSeek│            │ 陪练模型 + Skills    │
│ 只出 JSON 题卡 │            │ + 有上限的 Tools     │
└──────┬───────┘            └──────────┬──────────┘
       │ 题卡                            │ 工具调用
       ▼                                ▼
┌──────────────┐            ┌─────────────────────┐
│ author 校验   │            │ Math Workspace       │
│ BoardSpec V3  │───────────►│ lesson 课状态        │
│ first_question│            │ 前端确定性渲染       │
└──────────────┘            └─────────────────────┘
```

运行时 **Author 和 Tutor 不对话**。唯一耦合是那张题卡：前端带着 `card` 去 `/api/chat`，服务端把它编译进 Tutor 的系统提示（`card_guidance`）。

离线种子生产线里，Author 交卷后会用 Tutor 做一次「试教探针」，只检查有没有泄协议、有没有乱画，不把试教内容给孩子。

## 5. 出题 Agent

### 5.1 角色

出题作者是孩子看不到的人。它只做一件事：为当前主题写出**一张**有意思、有深度的探索题卡。

- **有意思：** 能动手或能猜，故事具体，答案不能一眼看完。
- **有深度：** 同一个道理有三层台阶——手上（做）、眼里（看出规律）、嘴里（说出为什么并接到一条公理）。

它不是老师。题卡里的 `insight` 是给 Tutor 的备课条，不是给孩子的讲义。

### 5.2 两层用法

**在线出题（上课时）**

1. 孩子选主题，前端先拿种子题卡，立刻能玩。
2. `POST /api/author` 同时可后台让强模型再出一张新卡。
3. 模型只输出 JSON → `normalize_card` → `validate_card` + `validate_board_v3`。
4. 失败则退回种子，不让孩子等、不把半成品题卡送进课堂。

默认引擎 GLM-5.3，备选 DeepSeek V4 Pro。Author 侧思考强制开。

**离线 Author Agent（种子生产线）**

1. 每个主题一次交 **恰好 3 张** 候选（工具 `author_submit_seed_batch`）。
2. 程序校验：字段、画板、三题不能只换皮肤、几何尺规题全组最多一题。
3. 再用主编模型评一批，最多 6 轮修订。
4. 通过后写入 `data/seed_catalog.json`，运行时优先于内置种子。

在线那次调用追求「这堂课有题可玩」；离线那条线追求「目录里的题经得起验」。

### 5.3 题卡里有什么

| 字段 | 给谁看 | 含义 |
|------|--------|------|
| `hook` | Tutor | 具体情景，换题时用来避重复 |
| `insight` | 仅 Tutor | 孩子最后要自己发现的那一个道理 |
| `axiom` | Tutor | 对准本主题哪一条公理 |
| `board` | 程序 | BoardSpec V3，六种 kind 之一 |
| `first_question` | 孩子 | 开场唯一一句；最终以程序从 board 推导的为准 |
| `ladder` | Tutor | `do` / `see` / `why` 三层各问什么 |
| `misconceptions` | Tutor | 孩子可能怎么误会 |
| `insight_key` | 程序 / 课状态 | 发现芯片的稳定键，不是给孩子念的句子 |
| `allowed_views` | 程序 | Tutor 换看法的白名单 |

Author **只描述模型、任务和揭示方式**，不能发明 type、steps、SVG、Canvas、Konva、坐标或画图代码。`board=null` 和旧的顶层 `semantic_board` / `diagram` 一律拒绝。

### 5.4 画板只能是这六种

| kind | 用来干什么 |
|------|------------|
| `layer_sum` | 分层物体合计；连续奇数围正方形时必须 stepwise |
| `path_count` | 有限步长的走法枚举 |
| `snap_grid` | 孩子往格子里摆方块 |
| `static_diagram` | 数轴、点阵、台阶、条形等受控静态图 |
| `geometry_compass` | 尺规正三角形（点、线、圆、三边相等） |
| `color_sequence` | 颜色周期排队 |

几何主题只准 `geometry_compass` 或 `snap_grid`，禁止数轴量长度。找规律必须用 `color_sequence`，不能用单色点代替花朵或珠子。

第一问不由 Author 自由发挥。程序读已校验的 board，生成一句口语、不泄底的 `first_question`（例如点格：先说几行几列、托盘几块、先放哪一排）。

### 5.5 出题失败怎么收

- JSON 解析失败、缺字段、board 不合法、9 块正方形误用 → 整张卡作废。
- 在线：立刻用该主题的种子卡。
- 离线：把问题列表打回 Author，整组三张一起改，不单张缝补。

## 6. 解题 Agent

### 6.1 角色

解题 Agent 就是孩子面前的小欧。它不「教这道题的标准答案」，而是规定**怎样陪孩子思考**：苏格拉底式追问，欧几里得式从少数公理往上建。

心里默默走波利亚四步——理解题目、拟定计划、执行、回头看——但嘴上一次只问一个问题。

### 6.2 两种陪练路径

| 条件 | 路径 |
|------|------|
| 探索模式，题卡带合法 V3 board | **Tutor Agent loop**：观察 → 工具 → 校验 → 再说话 |
| 带题来问，或没有 board | 纯文字流；无 board 时才允许 `xiaoou-draw` |
| 模型不支持 function tools | 自动降级为纯文字，画板保持上一张有效盘面 |

探索 + 有 board 时，**禁止**再输出任何画图 JSON。图已经由程序画了。

### 6.3 Agent loop

```text
读入：对话、题卡、课状态、工作区快照
   │
   ▼
拼系统提示 = 教学法 + 主题公理 + 题卡指导 + Skills + 可见工作区
   │
   ▼
最多 4 轮工具（每轮最多 3 个写工具）
   │  失败或达上限 → 注入「不要再调用工具」
   ▼
提交工作区新版本
   │
   ▼
对孩子说一句（流式，temperature 略高）
```

工具成功不等于数学正确。正方形、占用数、换看法，都要先过程序校验，Tutor 才能用嘴里的话认账。

### 6.4 Skills：策略，不是剧本

Skills 只告诉模型「这类情况通常怎么选工具、怎么问」，不向孩子提起名字，也不写成 `step 1 → step 2`。

| Skill | 用来判断什么 |
|-------|----------------|
| `euclidean_reasoning` | 从公理、定义、已建立结论出发，一次只接一个连接 |
| `socratic_tutoring` | 孩子是对、半对、猜、误会还是说不清 |
| `choose_representation` | 要不要换看法、改行数、改模型 |
| `test_conjecture` | 用最小正例或反例检验 |
| `concrete_to_abstract` | 先操作，再比关系，最后才命名 |
| `diagnose_misconception` | 算错、读图错、还是表示不合适 |

### 6.5 Tools：能做的动作

**只读：** 检查工作区、检查孩子看得见的投影、用程序核实一条数学声称（如是否围成正方形）。

**可写：**

- 画板注意：高亮、隐藏、揭示
- 积木：加块、排布（含「包一圈」与孩子按钮共用同一套 reducer）
- 编组
- 课记录：记下猜想、记下结论、记下孩子认可
- 换看法：只能落在题卡 `allowed_views` 里
- 点格占用：只能 `board_set_rows`，成功后嘴才能说新的数
- 走法 / 排队改模型：先 `board_set_model`

不允许的动作：执行 JS/HTML/SVG、直接改 DOM、口头假装画面已经换了、把 insight 写进可见文本。

### 6.6 课状态：台阶、削薄、发现

孩子看不见 insight，但课要记得「现在走在哪一层、已经发现过什么」。

```text
rung:     do → see → why
shrinks:  0..3     （点「太难了 / 再小一点」）
discoveries: [{ insight_key, child_said, topic }]
```

削薄是厚度旋钮，不是换题：

| 次数 | 程序做什么 |
|------|------------|
| 第一次 | 留在当前层，问句变短 |
| 第二次 | 从 why 退到 see，或从 see 退到 do；可以动一次画板 |
| 第三次 | 提议换一种看法或缩小数字；仍然不给答案 |

孩子自己跨上台阶，Tutor 才跟上去；不要为了走完 ladder 把孩子往上拖。

规律收束用固定问句：「你总结出什么规律了吗？」芯片上写孩子原话（≤80 字），并挡住 insight 的 8 字滑动窗口泄漏。换题保留发现；「开启新的探究」才清空。

### 6.7 开场为什么不经过模型

「开始玩」只做三件程序里的事：

1. 按题卡挂上 V3 画板和工作区；
2. 把 `first_question` 写成字幕和第一条小欧气泡；
3. **不调用** `/api/chat`。

模型第一次开口，是孩子动手、说话或画板里程碑之后。这样开场稳定、可测、不会被模型改成另一道题。

## 7. 中间层各自管什么

| 层 | 权威在哪 | 不管什么 |
|----|----------|----------|
| 题卡 | Author 生成，服务端校验 | 怎么教、怎么画像素 |
| BoardSpec V3 | `server/board.py` | 新 kind、临时协议 |
| Math Workspace | Tutor 工具写入，服务端 version++ | 孩子可见的讲稿 |
| 课状态 | 前端与 `server/lesson.py` 镜像 | insight 原文 |
| 渲染 | `web/board/*`、`web/activity/*` | 模型吐的 SVG |

点格占用是典型例子：格子里有几块，以 occupancy 为准。Tutor 想改数，必须先 `board_set_rows` 成功；失败就停在上一张图，不能嘴上改。

孩子在学具上走完一步（格子摆满、加上下一层、找到一条路），前端合成一条「孩子在学具上摆完了一步」的用户消息，再进 Tutor。画板事件和说话是同一条陪练回路，不是两套老师。

## 8. 一条完整回合

```text
选主题
  → 预取种子题卡（必要时后台再出新卡）
  → 点「开始玩」
  → 挂画板 + 程序写第一问        ★ 无 LLM
  → 孩子摆、说、或点「太难了」
  → POST /api/chat（带 card、lesson、workspace）
  → Tutor 观察工作区，可选调用工具
  → 一句追问回到字幕 / 气泡
  → 小欧问出固定规律句之后，孩子自己的总结变成芯片
  → 「换一题」：保留发现，台阶回到 do，新卡再走开场
```

Author 只出现在「选主题 / 换一题」这一下。开场之后，课堂只认题卡、课状态和工作区。

带题来问（拍照、打字）不走 Author。OCR 只读题、不解题；小欧先把看到的题目读给孩子确认，再从「这道题在问什么」开始问，不报答案。

## 9. 模型怎么配

| 角色 | 默认 | 思考 |
|------|------|------|
| 出题 | GLM-5.3，可切 DeepSeek V4 Pro | 强制开 |
| 解题 / 陪练 | 现有陪练模型（如 qwen3.7-plus） | 默认关，家长可开 |
| 拍照读题 | 视觉模型 | 只转写，禁止开始解 |

出题追求「题有深度、结构能过校验」；解题追求「短、稳、不泄底」。不要用同一个温度、同一套思考开关伺候两件事。

---

## 10. 必须守住的不变量

1. insight 不出现在字幕、芯片、气泡、画板标题里。
2. 开场 = `first_question`，禁止 LLM 改写开场。
3. 有 V3 board 时禁止 `xiaoou-draw` 和任意画图 JSON。
4. 点格数字以 occupancy 为准；改数必须先工具成功。
5. 正方形等结论，须 `math_check_claim` 或等价工具确认后才能说。
6. 规律问句固定，不可改写成「你发现了什么吗」之类。
7. 点格词表：蓝块 / 格子 / 上排 / 下排 / 托盘；不用贴纸、橘子等临时比喻。
8. V3 不新增 kind。几何种子只用 compass 或 snap_grid；尺规正三角形全组最多一题。
9. 9 块 3×3 不能当默认第一问。
10. 工具每轮有上限；失败回滚到上一版本，不把半成品协议给孩子看。

---

## 11. 和 V2 的边界

V1 这条链路是「题卡 + 对话 + 程序画板」。

V2（小欧数学世界 / 桥梁工坊）是另一条世界：孩子在体素工坊里动手，规则应由 `applyCommand` 和确定性介入来执行。V2 **不要**复用 V1 的 Author 题卡、Tutor 对话或 BoardSpec V3 当世界引擎。

以后若 V2 需要「出题」或「旁白」，仍然保持同一思路：出内容的模型不能直接改世界；改世界的入口只有程序。
